# 整套审阅与交付

结果：用户对实际页面的明确决定，以及与批准版本一致的可编辑 PPTX。

**先判宿主有没有 `review_open` 工具，再决定跑哪条**（这是 Agent 侧一眼可判的事，Skill 不猜环境）：

| 宿主有 `review_open` 工具（有插件） | 宿主没有（没有插件） |
|---|---|
| `… review --surface-only` —— 只生成页面、写 surface、校验 surface，**报出 surface 的绝对路径**；把它交给 `review_open`，面挂进 DSH 侧栏。**不起宿主、不开浏览器**（起了就有两套界面同时写同一个 `feedback.json`） | `… review` —— 生成页面与 surface、起无插件宿主（`serve-review.mjs`）并打开浏览器 |

两种模式跑的都是同一份页面、同一个 surface，审阅语义完全一样；差别只在"谁 serve 它"。

运行 `python scripts/orchestrate/ppt_pipeline.py <project> review`（或 `--surface-only`；`--no-host` 是同义别名）。Controller 检查当前版本、生成审阅页与 **surface**（`_internal/05_review/review-surface.json`）。权限问题按宿主流程申请；不能只打印链接就当作已经展示。

**页面必须"没有桥也把自己画出来"——桥是增强，不是氧气**（公共规则）：审阅页先用**页面自带的 data** 把逐页卡、导航、状态/进度画出来，**再去** `ReviewBridge.connect()`；握手有上限（`BRIDGE_TIMEOUT_MS`，不落地就按"没有桥"降级继续），连不上时页面**自己说出来**「本页只读 —— 内容可以看，反馈存不进去」。渲染**不许**挂在握手、网络或任何外部依赖上；**不许在顶层裸用 `localStorage`／`sessionStorage`**（不透明源 iframe 里读它会直接抛 → 整页脚本当场死、**零报错**，用户只看到空白页）。页面上常驻一个「重新加载」出口，它不依赖任何告警出现。

**审阅面是公共件 `planners-review-core` 的缝**：页面是 surface 的入口（`02_visual_review.html`，里面只留一个**独立成行**的 `{{REVIEW_BRIDGE}}` 注入点，**不放桥的副本**（宿主把它换成整段注入：无插件宿主是 `base` + `<script src>`，插件内联桥源码）），宿主负责显示、serve 资产、落文件、唤醒模型。有 DSH 插件时宿主是侧栏 iframe；没有插件时是 `node <公共件>/scripts/serve-review.mjs "<surface.json>" --port 0`（本 Skill 用它，见 `scripts/review_surface.py`）。**页面代码两份宿主完全一样**，分支全在桥里。

**判断宿主死活要用 HTTP GET**（拿 `_internal/05_review/review_host.json` 里的 URL 读回页面本身，**并且逐字节等于磁盘上那一份入口**），不要用端口探测：进程被外部清掉之后，端口上的 socket 仍可能接受 TCP，`nc -z` 会假报 OPEN，而 HTTP 请求拿到的是空响应；端口也可能已经被别人的页面占了，只有内容能证明它端的是我们的页面。`review` 每次都会自己重新确认一遍；宿主没了就重启并返回新 URL（活着的宿主会复用，URL 不变——重出的页它按请求读盘，页面刷新就是新的）。

界面一次展示一页，包含全套导航、当前／前版切换、区域标注、页级反馈、图片上传替换与裁剪、新增图片。灰／绿／橙只代表未处理／人工批准／要求修改。图片或意见改动必须转为待修改。

**提交有两个口，逐页提交才是唤醒点：**

- **「本页要求修改」／「本页通过」= 写整份状态 + `wake({unit: <page_key>})`** —— 一次只定一页，模型收到的那句话就是「`<page_key>` 已定；只重出这一页，其余页不要动」。整份状态照旧（`review_id` ＋ 覆盖全部页），所以「必须看过当前版本」这条保护不变。
- **「整套提交」= 写反馈文件 ＋ 整句覆盖唤醒**（`wake({unit:'整套', text:'整套已定，可以进入下一步。'})`）：surface 的 `wake.text` 是逐页口气，直接套会说成"整套 已定；只重出这一页"，所以这一路**自带整句话**。没有插件时它同样只落日志，人回对话说一声「已完成」也行。
- **上传控件按宿主的 `review.capabilities` 决定**：surface 声明了 `asset-upload` 才显示「新增图片／替换图片」，没声明的宿主下整块隐藏；页面不自己在本地判断这个能力。`test_review_browser` 有断言钉住"能力真的交到了页面手里"。

**一条意见的生命周期：意见 → 模型改 → 那条意见结束。** `resolve --feedback-id` 一跑，这条意见就**关闭**了——它是**历史**，不是"还挂在人名下的待办"：同页同话**永远不再成为条目**（内容身份记进 `resolutions.json` 的 `closed`；`consume` 会把它算进 `review_intake.suppressed` 并打印，不静默）。**让人回头清空自己的意见才算数，等于把模型的收尾工作转嫁给人**——2026-09-26 真人使用当场打回。**"有意见不许批准"只约束"人刚写下的新意见"**，不约束已经落实的历史。

**上一轮的意见随页面回来，但它是「只读上下文」，不是本轮的意见。** 被重出的页（版本变过）在新审阅页上带回它上一轮的 `previousDecision`／`previousFeedback`／`previousAnnotations`／`previousAssets`，页面把文字、框选、图片改动都显示在「上一轮你说的（这一页已按它改过；只作参考，不算本轮意见）」那一块里——**只显示，不预填进 `feedback`／`annotations`／`assets`**。所以这类页初始就是「未处理」，**一次点击就能批准**；整套提交（含"批准未处理页"）也能覆盖它。

  **为什么强调"不预填"**：预填进的是**参与判定的输入**，于是同一段字既被当成"上一轮我要过什么"，又被当成"本轮我有什么意见"——页面自己判成 `revise`、整套提交跳过它、`items` 里再生一条与上一轮完全相同的待办（用户看到"整套已定"，记录里那页却还是"要求修改"）。**一句话只该有一个身份。** 人若想接着上一轮的话继续提意见，自己复制过去改——那是**新意见**，该生成新条目。

  版本没变的页不带这些字段，它们的批准由 `approvals()` 原样保留。

**"通知到了"与"通知被核过"是两件事，页面分开说。** 逐页/整套提交后，页面按 `review.wake()` 的返回分档：宿主回了 `verified`（去会话日志里核对了进入队列）→「已通知模型（宿主已在会话日志里核对进入队列）」；**没回** →「已通知模型（宿主未核对 —— 若模型迟迟没反应，请回对话说一声）」。没有插件时宿主不回这个字段，所以那一档说的就是实情。核验结果还写进 `feedback.json` 的 `provenance.wake`（同一份 payload、同一个 `submitted_at` 补写一次，**不是第二轮提交**；收件按 `submitted_at` 去重），将来回看这一轮时"通知有没有到"有据可查。

**唤醒语自带决定。** 逐页提交用**整句覆盖**（不套 surface 的模板）：要求修改是「`<page_key>` 要求修改：<意见要点> —— 只重出这一页，其余页不要动。」，通过是「`<page_key>` 已通过。」。以前统一说「X 已定」，人点的是"要求修改"时模型得先翻 `feedback.json` 才知道；现在唤醒语本身就是判断依据。surface 的 `wake.text` 模板只留给不覆盖的调用方（例如整套提交那条路）。

**模型重出一页之后，页面上的图会自己换（不用刷新）。** 宿主只 `stat` surface 里 `watch` 的那几项（本 Skill 是 `snapshot.json`），**它不知道什么变了**；戳到页面之后是**页面自己去读 `snapshot.json`、自己 diff**：只把版本变过的那几页的 `<img>` 换成新图（当前页的舞台图 + 轨道缩略图），把它们的决定退回「未处理」（画面换了，旧批准不算数），并更新内存里的 `review_id`（否则下一次提交会被判成上一版）。**不整页重载**——滚动位置、别的页已填的意见/框选、正在编辑的输入框一律不动。切换回被重出的那一页会看到「这一页的画面已更新（模型按意见重出过）：复核新图后清空这一页的意见即可批准。」，轨道上那页的圆点变蓝。

**排查「模型改完了但图没变」先看页面上那一行「变化戳：N 次 · 最后 HH:MM:SS」**（和连接状态同一块）：**没有戳** = 宿主没认 `watch` / 没推（宿主侧的事）；**有戳但图没变** = 页面这一侧（diff 没算出差异、或资产取不到）。没有这一行就只能猜。注意戳是**变化驱动**的：页面加载后的第一个采样周期只建立基准，在那之前改文件不会产生戳。

**陈旧提交在页面这一侧就被拦住。** 页面提交前拿当前 `snapshot.json` 比一次 `review_id`：对不上（模型已经重出过审阅页）就显示「这一页已更新，先复核：<哪几页>」并且**不写文件**——人写的字不会因为一次过期提交而盖掉别的。模型侧还有第二道：`next` 收件时（`consume`）算出这份反馈绑的是不是当前这一版，对不上就报 `feedback.stale`，它**不算批准**（`approvals()` 按版本比），但它的 items 仍然是模型要继续处理的东西。

**留档在收件那一刻发生。** 每一轮被模型读到的反馈都会留一份到 `_internal/05_review/history/round-NN.json`（`next` 的输出里 `review_intake.archived` 说明写到哪一份）。`feedback.json` 只有一份、宿主每次整份覆盖，所以「上一轮这一页到底提了什么」只能读 `history/`。

**读反馈时先按框选的坐标把那块看一遍。** `annotations[].{x,y,w,h}` 是**归一化**坐标（0–1、相对页面），换算成像素（`x*1920, y*1080, w*1920, h*1080`）后从 `_internal/03_png_preview/pages/<page_key>.png` 裁出那一带再动手——"底部没对齐"这样的五个字，配上坐标就能定位到"横轴比柱组两端各出头 140/200"这种实体缺陷；没有坐标，同一句话至少对应三种改法。框到接近整页（`w>0.9`）时按"整页重做"处理，不是"某处小修"。

用户实际提交反馈后继续。读取所有反馈（`feedback.json` 已被 `consume` 规范化：决定、`items`、每页盖上的版本与 PNG hash）；修改回到统一创作阶段。修改后的页面重新检查和审阅；未变化页面可保留其版本一致的批准。禁止模型调用反馈接口代替用户批准生产项目。

## 审阅页的观感：用 DSH 的令牌（vendor 一份副本，别手改）

页面的颜色、字、圆角、阴影、滚动条、控件密度都走 DSH 的设计令牌，表在
`assets/review/dsh-tokens.css`。它是**副本**（审阅页在不透明 iframe 里继承不到宿主的变量，
外链样式表也会被 403 打回，所以令牌只能随页面一起内联发出去）。

**更新方式只有一条**：

```bash
python3 scripts/vendor_dsh_tokens.py        # 从 npm 包 + 本机发行版重抄
```

它会打印并写进文件头：三个源文件的 sha256、补丁 token 条数。**手改那份 CSS 会漂移，而两边都不会报错** —— 所以别手改。缺 npm 包或缺发行版时脚本直接报错退出，不会写出半份。

**只认一个来源：本机已装的发行版。** 脚本读 `Info.plist` 的版本，再从 `app.asar` 里的
`lib/welcome/welcome.css` 抽表（那是整个发行版里唯一带这份表的文件），另补它没有的
`--dsw-radius-*`、运动变量、字体栈底座。

**别用 `npm view <包> version` 取版本** —— 它跟 `latest` 标签，而 `dsh-client-ui-theme` 的
`latest` 卡在最老那一版（`0.0.1-rc.1`，8-10）；照它抄会得到比运行版本老七周的副本，
而且**不会报错**。这个坑已经踩过一次，见 maintenance-history。

**页面里写规则时的三条**：

1. **颜色/字/圆角/阴影一律用 token**，不写字面值（写死一个 hex，明暗就废了一半）。
2. **字用组合式 token**：`font: var(--dsw-font-xs-strong-13)`，别自己拼 `font-size` + `font-weight` —— 他们的 UI 粗体是 **500**，行高是**固定档位**，自己拼就会回到"看着像但不是"。
3. **内容是内容，UI 是 UI**：缩略图卡、被审的那张幻灯片本体**不套** UI token（那是作者的画面，不是我们的界面）。

**明暗**：`body[data-ds-dark-theme]` 那一整套已在表里。页面在 iframe 里读不到宿主的偏好，所以跟随系统（`prefers-color-scheme`）——就是 DSH "system" 那一档；宿主将来若自己把这个属性打进来，页面的那句不会覆盖它。

**层次怎么读**：`bg-base` 画布 → `bg-module-platform` 侧栏凹面 → `bg-document-preview` 被审的纸 → `bg-layer-1` 浮层；分隔一律用 `border-l1/l2` 细线，不要用灰块。

**控件密度**：他们的控件是**固定高 + 只给水平内边距**（按钮 28、紧凑按钮/指标 24），不是垂直内边距堆出来的 —— 加新控件时按这个来。

## 作者直接在页面上改的那一笔，是**定版**，不是建议

作者可以在审阅页上直接改字、拖动位置、删元素（`svg_edits`）。这一笔在 `consume` 时被**确定性写回 `_internal/02_svg_source/<page_key>.svg`** —— 写进去就是那一页的定版，**不经过你**。

**它有一个敌人：你自己。** 同一页有两个写手 —— 作者的直改，和你的生成脚本。脚本是整份重写，作者那一笔不在脚本里，于是静默消失。真人实测（2026-10-05）：作者手改过多笔，其中几笔被后续的整批重跑覆盖，原话是「我白改了」。**生成的作用域规则见 `04_svg_stage.md`**（一次只写被点名的页）；下面是机器这一侧的兜底。

**账本。** 每一笔直改都在 `_internal/05_review/applied_svg_edits.json` 留一条：`edits`（逐笔内容，不只是哈希）、`old_version`／`new_version`、`svg_sha256`、`svg_snapshot`、`applied_at`。写回时**连带把人改完那一版 SVG 快照到 `_internal/05_review/versions/<page_key>-<version>.svg`**（PNG 本来就有这个待遇；源文件反而没有，所以人改掉的东西以前找不回来）。

**闸门。** 只要账本说这一页被人改过，就比一件事：**当前这一版还是人改完那一版吗？** 不是、而且没人交代过，就按「人的改动被静默丢掉」处理：

| 入口 | 表现 |
|---|---|
| `next` | 返回里带 `human_edits_lost`（含逐笔 `edits` 与快照路径）＋一句 `human_edits_lost_zh`；**入口就说，不等你自己去比账本** |
| `check` | 那一页被标成 `fix`，附 `human_edit_error` |
| `export` | 检查画面直接拦下，不转换 |

**交代。** 处理完（把那一笔带进新版／恢复／确认被新版替掉）跑：

```bash
python scripts/orchestrate/ppt_pipeline.py <project> ack-human-edit --page <page_key> --note '人那笔改字已按原意带进新版标题'
```

`--note` 要写清实际做法，空话不算（和 `resolve` 同一条规矩）。交代**按版本记账**：再画一次这一页，闸门会重新立起来 —— 上一次的交代只对上一版有效，不是永久免死金牌。

**不要自动回放人的那一笔。** `svg_edits` 的定位是**元素树路径**（`0.5.4.0` 这种）。页面一旦重画，同一个路径指向的就是另一个元素，自动套回去会改坏别的东西。所以这条路只能是「停下来 + 人/模型重新落一遍」，快照是给人看的还原底本，不是自动补丁。

审阅走完（或用户明确要求先出稿）后运行：

```bash
python scripts/orchestrate/ppt_pipeline.py <project> export
```

转换器严格缺图，按底稿顺序导出文字、图形、图片和 notes。仅 Controller 调用 converter；导出成功不等于最终视觉一致。

**导出不再要求"整套人工审阅已批准"。** 审阅仍然要做，但它不是导出的前置门——强制人点到最后一页才能导出，既拦不住也救不了：没审完就导出，人还是会回来改。该由机器保证的是**导出质量**（描边粗细不缩水、文字不出边距、图片不丢），那由转换器、**导出时的检查画面**和 `scripts/test/test_converter_geometry.py` 负责，不靠人守门。

**导出时机器做两件事：**

1. **跑检查画面。** `export` 在转换之前逐页跑一遍技术检查，用的是**和转换 PPT 同一套坐标几何**（校验器直接调用转换器的坐标模型，不再自己算一份）。有错误就拦下不出稿——这类错误正是「转成 PPT 会坏」。
2. **提醒审阅。** 如果这套页面还没走过整套人工审阅，导出的返回里带 `review_reminder`：**把这句话转给用户**，问他现在要不要审。这是个提醒，不是门——导出已经完成，随时可以补审。

审阅与模板审阅是**两个主体**（页面审阅的单位是 `page_key`，模板审阅的单位是 registry 里的 `layout_id`），各有自己的页面、决定词汇与判据，**不要合并**。两者共同的是「必须看过当前版本」这条保护：提交都要带生成审阅页时写下的 `review_id`，旧标签页不能批准新版本。

## 验证的是文件，不是渲染结果

回渲染有两种毛病：**同源验证**（验证用的渲染器和被验证对象共用同一套转换逻辑，分不清"文件坏了"和"这个渲染器不画这么细的线"），以及**验"像不像"而不是"对不对"**（两个排版引擎的字宽行高本来就差一点，"看起来差不多"只能证明在那一款软件里差不多）。

所以：**先读 PPTX 文件本身**。页数、文字/图形可编辑性、图片数量与比例、每根描边的线宽、每个文本框的边界，都能直接从文件里断言，与用哪款软件打开无关。这类"值不对"的错误占实际问题的绝大多数——描边被缩到 60%、长段越出右边距 45px，都是文件里的值不对，不是渲染器不听话。

然后把渲染器当**第二意见**用：用当前环境的 PowerPoint、LibreOffice 或可用的 PPTX 渲染工具把最终文件渲染到项目内，只用来发现明显崩坏（缺图、错位、空页、整页空白）。处理会改变画面的错误后重新走受影响页面审阅。查看最终渲染后记录：

```bash
python scripts/orchestrate/ppt_pipeline.py <project> export-inspect --previews <project内实际PPTX渲染文件...> --note '逐页对照结果与已接受差异'
```

**结论措辞要与证据强度一致**：在 LibreOffice 里渲染无崩坏，就写"在 LibreOffice 下无崩坏"，不要写成"与批准稿一致"——后者是它证明不了的。用非目标渲染器时同时登记已知的系统性差异（例如基线偏移的像素量级）。

缺少渲染能力时明确交付限制，保持 EXPORT_VERIFY，不能声称 COMPLETE。最终打开 PPTX 和审阅结果。事实正确、品牌一致和内容质量需要真实人工判断，机器绿色不替代这些判断。
